# Connection and network policy technical design

Scope: E11-2 owns owner connections, OAuth, the secret store and credential broker, network policy, and the single work dispatch gate with its executor port. E11-1 supplies `AuthContext`, `AgentInstance`, `BudgetPort`, `AuditEvent` and `ActionConfirmation` (see [aicl-control-plane/technical.md](../aicl-control-plane/technical.md), including the shared error taxonomy, conventions and gate-reason vocabulary). E11-5 builds the pages that call these operations. Source locations are proposed under `backend/aicl/connections/`, `backend/aicl/network/` and `backend/aicl/work/`. E11-2 registers its routes by adding its router factory to the E11-1 `ROUTE_FACTORIES` extension point and its real ports to the E11-1 port registry (see AppComposition in the control-plane document); it tests them through the E11-1 `create_app` and test server.

## Contracts

### Connection (owner E11-2)

`Connection {id, owner_id, tenant_id, provider, display_name, status, granted_scopes, secret_ref, provider_revoke_status, created_at, revoked_at, version}`. `secret_ref` is an opaque identifier of the encrypted secret; the credential value is never part of this model, any API or tool result, an audit event, a log line, the chat or the agent context. `provider` is `gmail | reddit`. `display_name` is 1 to 80 characters chosen by the owner (no provider account identifier is stored or shown). `status` is `active | reauthorization_required | revoked`; `provider_revoke_status` is `not_applicable | succeeded | failed` and is set only on revocation. `secret_ref` is null once revoked. Connections are visible only to their owner; another owner's connection is `not_found`.

### ConnectionAttachment (owner E11-2)

`ConnectionAttachment {id, instance_id, capability, connection_id, owner_id, tenant_id, created_at, detached_at}`. At most one active attachment per `(instance_id, capability)`; one connection may have active attachments on many instances of the same owner (D11-13). Only capabilities with a provider (`gmail.*`, `reddit.*`) can have attachments.

`attach_connection(auth, instance_id, expected_version, capability, connection_id) -> MutationResult` requires: instance and connection both owned by `auth.owner_id` (otherwise `not_found`), instance not archived, connection `active`, capability provider equals the connection provider, and the connection's `granted_scopes` contain the capability's required scope from the table below (otherwise `validation_failed` with `scope_missing`). It replaces any existing attachment for that capability. `detach_connection(auth, instance_id, expected_version, capability)` detaches; an active instance whose capability then has no attachment is gated `connection_revoked` only when dispatch next requires it. Both bump `version`, append `connection.attached` or `connection.detached` and follow the version rules of the instance operations. `attach_connection` calls `evaluate_gate_control` and clears a persisted `connection_*` gate only when every capability in `gate_context.capabilities` now has an active attachment on an `active` connection.

### Revocation (owner E11-2)

`revoke_connection(auth, connection_id) -> RevokeResult {connection, detached_instance_ids, provider_revoke_status}` is idempotent. It is an action, separate from any later use request:

1. Transaction A: set `status=revoked`, detach every attachment, set `gated_reason=connection_revoked` with `gate_context.capabilities` (the capabilities it had been attached to) on active instances that had an attachment, bump their `version`, append `connection.revoked` (details: `provider`, `connection_id`). From this commit on the connection cannot be used, because the broker checks status before reading any secret.
2. Provider revoke: the broker reads the secret once and calls `ProviderOAuthPort.revoke` with a 5 second timeout.
3. Transaction B: destroy the secret (`SecretStore.destroy`), set `secret_ref=null`, `provider_revoke_status` to `succeeded` or `failed`, append `connection.provider_revoke_succeeded` or `connection.provider_revoke_failed`.

If the provider call fails or the process stops between steps, the credential is still destroyed locally: a startup sweeper (`RevocationSweeper`, an E11-2 `STARTUP_HOOKS` hook that runs before the reconciler and exposes `run_once()`; if it cannot complete, startup fails, fail closed) destroys the secrets of every revoked connection that still has one and records `failed`. The UI then tells the owner that access must be removed in the provider's own account settings. Historical audit events and usage stay visible with redaction.

### NetworkPolicy and authorize_destination (owner E11-2)

`NetworkPolicy` is the immutable fixed allow-list in the table below (code constant, not environment-configurable) plus an instance's owner-added exact domains. Two functions share one result type `NetworkDecision {allowed, reason, rule}`; `reason` is `allowed`, `unknown_capability`, `capability_not_networked`, `host_not_allowed`, `scheme_not_https`, `port_not_allowed`, `userinfo_not_allowed`, `ip_literal_not_allowed`, `address_not_public`, `method_not_allowed`, `path_not_allowed`, `redirect_limit` or `policy_unavailable`:

- `check_destination_rules(policy, domains, capability, method, url, hop_index) -> NetworkDecision` is a pure function with no I/O: it checks the capability, scheme, port, userinfo, IP-literal and host forms, the exact-host, path-prefix and method rules and the hop limit. It never returns `address_not_public`.
- `authorize_destination(instance, capability, method, url, hop_index, resolver) -> NetworkDecision` calls `check_destination_rules`, and only when that allows, resolves the host through the `Resolver` port and returns `address_not_public` unless every returned address is a public unicast address. The classification of resolved addresses is a second pure function, `classify_addresses(addresses) -> allowed | address_not_public`. Both functions are unit-tested without network; the second is tested with the fake resolver.

Missing policy or an unknown capability always denies. There are no wildcard rules, no deny-rule evaluation and no pattern matching: a destination is allowed only by exact host (and path prefix and method for fixed endpoints) match.

Capability to provider to scope to fixed endpoint table (a design value; exact provider scope strings and hosts must be re-verified against official provider documentation as part of the separate enablement, which stays out of this design):

| Capability | Provider | Required OAuth scope | Fixed allowed endpoints (https, port 443) | Connection | Per-action confirmation |
|---|---|---|---|---|---|
| `inference` | none | none | none (fake model only; no real adapter) | no | no |
| `gmail.read` | gmail | `https://www.googleapis.com/auth/gmail.readonly` | `gmail.googleapis.com`, GET, prefix `/gmail/v1/users/me/` | yes | no |
| `gmail.send` | gmail | `https://www.googleapis.com/auth/gmail.send` | `gmail.googleapis.com`, POST, `/gmail/v1/users/me/messages/send` | yes | yes |
| `reddit.read` | reddit | `read` | `oauth.reddit.com`, GET | yes | no |
| `reddit.post` | reddit | `submit` | `oauth.reddit.com`, POST, `/api/submit` | yes | yes |
| `network.fetch` | none | none | none fixed; owner-added exact domains only (GET and HEAD) | no | no |

OAuth endpoints are used only by `ProviderOAuthPort` and are never available to a capability: Gmail `accounts.google.com/o/oauth2/v2/auth`, `oauth2.googleapis.com/token`, `oauth2.googleapis.com/revoke`; Reddit `www.reddit.com/api/v1/authorize`, `www.reddit.com/api/v1/access_token`, `www.reddit.com/api/v1/revoke_token` (Reddit authorization requests `duration=permanent` for a refresh token).

### SSRF guard for owner domains (owner E11-2)

`normalize_owner_domain(raw) -> host` is the only way a domain enters `network_domains`, and `check_destination_rules` applies the same rules to every request URL and every redirect hop (`authorize_destination` adds the address check):

- Scheme must be `https`; port must be absent or 443; userinfo (`user:pass@`) is rejected; no fragment-as-host tricks, and the URL parser used is the standard library's `urllib.parse` with a strict check that the parsed `hostname` equals the lowercase ASCII host.
- The stored value is a bare host: lowercase ASCII DNS name, 1 to 253 characters, labels `[a-z0-9-]{1,63}` not starting or ending with `-`, at least two labels, IDNA names accepted only in their punycode form (`xn--`). No trailing dot, wildcard (`*`), path, query or port in the stored value.
- IP literals (IPv4, IPv6, decimal, hex, octal or bracketed forms) are rejected, as are `localhost`, `*.local`, `*.internal` and single-label names.
- At request time `authorize_destination` resolves the host through the `Resolver` port and every returned address must be a public unicast address: loopback, private (RFC 1918, RFC 4193), link-local (including `169.254.169.254` and other cloud metadata addresses), CGNAT, multicast, reserved and unspecified ranges are `address_not_public`. DNS pinning (connecting to the validated address instead of re-resolving, to defeat DNS rebinding) applies only to a future real outbound executor, which is provider enablement and is not part of this design (the DR-14 safeguard keeps it disabled); that executor must connect to the address returned by `authorize_destination`. The MVP fake executor makes no network call, so pinning has no MVP implementation or test.
- Redirects are not followed automatically. Each hop (`Location`) is re-authorized as a new request with `hop_index+1` against the same capability and the same instance domain list; more than 3 hops is `redirect_limit`.
- A domain edit is an owner UI operation (`add_network_domain`, `remove_network_domain` in the instance operations); removing a domain takes effect for the next authorization. The MVP's executors are fakes, so the guard is proven by unit tests on `check_destination_rules`, `classify_addresses` and `authorize_destination` with the fake resolver, and through the gate; no live network call is made.

### SecretStore and CredentialBroker (owner E11-2)

`SecretStore` (Protocol): `put(owner_id, connection_id, field, plaintext) -> secret_ref`, `get(secret_ref, owner_id, connection_id) -> bytes`, `destroy(secret_ref)`. The MVP implementation encrypts with AES-256-GCM using the key from `AICL_SECRET_ENCRYPTION_KEY` (base64, 32 bytes), a random 96-bit nonce per value and AAD `owner_id|connection_id|field`; a value moved to another record fails to decrypt. `destroy` overwrites the ciphertext and sets `destroyed_at`; `get` on a destroyed or mismatched reference raises `SecretUnavailable`. Fields are `access_token`, `refresh_token` and `expires_at`. Only the broker and the revocation path hold a `SecretStore`.

`CredentialBroker` (Protocol): `call(authorized_work, operation) -> ProviderResult {status, response_summary}` where `operation` is a provider operation id from the table (`gmail.messages.list`, `gmail.messages.send`, `reddit.listing.read`, `reddit.submit`) with a bounded payload. The broker is the only component that sees credentials and credentials stay outside the agents (D11-6, D11-12): it re-checks that the attachment is active and the connection `active` (otherwise `connection_unavailable`), re-authorizes the provider endpoint through `authorize_destination`, reads the secret, refreshes the access token when expired (a failed refresh with `invalid_grant` sets the connection to `reauthorization_required` and denies), applies the credential inside its own outbound request through `ProviderOAuthPort.call`, and returns only a status and a bounded redacted response summary. No credential or token, short-lived or otherwise, is returned to the gate, executor, chat, tool, UI or logs. Errors: `connection_unavailable`, `secret_unavailable` (store or key unavailable, which denies and does not retry), `provider_error`, `endpoint_denied`, all mapped to `denied`/`unavailable` of the shared taxonomy without detail.

Before persisting refreshed credentials, the broker rechecks the active connection,
its version and original credential references in the same write transaction as
the replacement. If revocation or another refresh changed that authority, the
stale refresh is denied without creating secrets or restoring revoked access.


### ProviderOAuthPort (owner E11-2)

Protocol methods: `authorization_url(provider, scopes, state, code_challenge, redirect_uri) -> str`; `exchange_code(provider, code, code_verifier, redirect_uri) -> TokenSet {access_token, refresh_token | None, expires_at, granted_scopes}`; `refresh(provider, refresh_token) -> TokenSet`; `revoke(provider, token) -> None` (raises `ProviderRevokeError`); `call(provider, operation, access_token, payload) -> ProviderResult`. `FakeProviderOAuth` is the only enabled implementation: its authorization URL points at an in-app `/fake-provider/authorize` page, registered only in the test and development compositions (`AICL_ENVIRONMENT` is `test` or `development` and `AICL_PROVIDER_MODE=fake`; the router factory is not added otherwise and the route returns 404), it accepts codes of the form `fake-code-<scenario>`, can be scripted to grant fewer scopes, fail a refresh or fail a revoke, records every call for assertions, and makes no network call. A real adapter for Gmail or Reddit is provider enablement, which is not part of this design and is rejected at startup (see Configuration).

OAuth flow:

- `begin_oauth(auth, provider, capabilities) -> {authorization_url}`: scopes are the union of the required scopes of the requested capabilities. It stores `OAuthState {state_hash, owner_id, session_id, provider, scopes, pkce_verifier_ciphertext, created_at, expires_at, used_at}` where `state` is 32 random bytes (URL-safe base64, stored as SHA-256 hash), the PKCE verifier is 64 random characters and the challenge is S256. State expires after 600 seconds and is single use. The redirect URI is exactly `AICL_PUBLIC_BASE_URL` + `/connections/oauth/callback`.
- `GET /connections/oauth/callback?state&code` (route owned by E11-2) requires the session cookie. It looks up the state by hash and requires: unused, unexpired, same `session_id` and `owner_id`, matching provider. It marks the state used before exchanging the code, exchanges with the stored verifier, requires the `granted_scopes` set to equal exactly the requested scopes, stores the tokens through `SecretStore`, creates the `Connection` and appends `connection.created`. Provider `error` parameter, a state mismatch, replay, expiry, missing or extra scope, or exchange failure creates no connection, stores no provider credentials, destroys nothing else, appends `access.denied` where identity mismatched, and redirects to the Connections area with a generic message. The code, state and tokens are never logged or echoed.
- Refresh and revocation are broker behavior as above.

### WorkAuthorization (owner E11-2)

The single dispatch gate. It is the only path that can start inference, compute, provider use or network use, so `BudgetPort`, `authorize_destination`, confirmation consumption and the broker all have this production caller. `WorkRequest {instance_id, work_id, capability, payload, estimate, destination_url}`: `work_id` is a client-generated idempotency key (16 to 64 characters `[A-Za-z0-9_-]`, key pattern in the control-plane Conventions; the simulated-work form derives `work_<32 hex>`), unique per tenant; `payload` is a JSON object of at most 16 KB; `estimate` is the BudgetPort `Estimate`; `destination_url` is required only for `network.fetch`.

`authorize_and_dispatch(auth, request) -> WorkResult {work_id, outcome, denial_reason, pending_action_id, usage, hold_state}` with `outcome` of `succeeded | failed | unknown | denied`. Every dispatched request is stored as `WorkRequestRecord {tenant_id, work_id, request_digest, outcome, hold_id, created_at, updated_at}` (table owned by E11-2; `request_digest = sha256(canonical_json({instance_id, capability, payload, estimate, destination_url}))`; `outcome` is `pending | succeeded | failed | unknown | released`). It is inserted in the step-9 transaction together with the hold and updated in the same transaction as each `settle`, `mark_unknown`, `release` and `reconcile`. A repeated `work_id` after a dispatch returns the stored `WorkResult` rebuilt from the record, the hold and the usage (a different request digest is `conflict`); denials are not stored under the `work_id`, so it can be retried after the owner fixes the cause. Confirmed resubmission: the denial page carries the request payload in the confirmation form (nothing sensitive is persisted by `PendingAction`), and after `POST /pending-actions/{id}/confirm` the owner resubmits it with the same `work_id`; the gate recomputes the digest. A replay of an already executed confirmed request uses a new `work_id` with the same payload and is denied `confirmation_used`. Fail-closed check order (first failure denies, later checks do not run, and any exception or unavailable dependency denies as `check_unavailable`):

1. Identity: `auth` is current. 2. Instance exists in `auth.tenant_id` (otherwise `not_found`). 3. `lifecycle == active` (`instance_not_active`; no gated reason is persisted). 4. Capability grant enabled (`capability_disabled`; sets `gated_reason`). 5. Estimate present and bounded (`estimate_missing`). 6. For `gmail.send` and `reddit.post`, a valid unused unexpired `ActionConfirmation` for the computed digest exists, otherwise `confirmation_required` (creating or reusing a `PendingAction`), `confirmation_expired`, `confirmation_used` or `confirmation_mismatch`. 7. For provider capabilities, an active attachment on an `active` connection (`connection_unavailable`; sets `gated_reason`). 8. Network: for provider capabilities the capability's fixed endpoint, for `network.fetch` the `destination_url` against the instance's owner domains, through `authorize_destination` (`network_denied`; sets `gated_reason`). 9. In one `db.transaction()` with one `conn`: `BudgetPort.reserve(conn, ...)` (daily and monthly, both categories) and, for confirmation capabilities, `consume_confirmation(conn, ...)` (connection-scoped forms from the control-plane document). Any denial or a consumption that changes no row rolls both back (a lost consume race, where a concurrent dispatch consumed the confirmation first, is `confirmation_used`; `budget_exhausted`, `budget_unavailable`, `price_unavailable`, `reconciliation_pending`, or `confirmation_*`). After the rollback the gate writes `gated_reason` and `gate_context` (for the budget reasons) and the `work.denied` audit event each in their own transaction, because a denial changes no other state. 10. Dispatch through `WorkExecutorPort.execute` (with `connection_handle` being the opaque attachment id only). Every denial appends `work.denied` with `denial_reason`; a dispatch appends `work.dispatched` and the budget events.

The step-9 write transaction is the authorization boundary for a new dispatch. Before reserving, it re-reads the authenticated owner's instance, verifies that the authentication has not expired, the lifecycle is still active and the capability is still enabled, and rejects any persisted gate. Window rollover alone cannot clear that gate; an owner operation must resolve the control. It then requires the current instance version to match the version used for the earlier network checks and re-checks the provider attachment/connection, requiring the same attachment identity. A changed version or attachment denies as `check_unavailable`; the caller can retry against current policy. DNS resolution stays outside the write lock. Owner changes committed before this transaction take precedence; changes after the committed work intent govern subsequent requests and do not cancel work already accepted. Reservation, confirmation consumption, work intent and dispatch audit remain one transaction.

Outcome handling: `succeeded` or `failed` with measured usage calls `settle`; `not_started` calls `release`; `unknown`, an executor exception or a timeout (`AICL_EXECUTOR_TIMEOUT_SECONDS`) calls `mark_unknown` and the result is `unknown`. Each is a connection-scoped call in its own transaction with its audit event and the `WorkRequestRecord.outcome` update. A `settle` that finds the hold already `released` (for example released by the reconciler) is `conflict`, and the late usage is audited as `budget.late_settlement`, never dropped.

Reconciler (owner E11-2; `HoldReconciler`, registered after the `RevocationSweeper` in `STARTUP_HOOKS`) runs at startup and every `AICL_RECONCILE_INTERVAL_SECONDS` in-process, with `run_once()` for tests. For every `unknown` hold and every stale `held` hold it calls `WorkExecutorPort.lookup(hold_id)`. The globally unique hold identity prevents equal tenant-scoped `work_id` values from colliding in executor state. A definite measured outcome settles through `reconcile`; `not_started` releases a held reservation or reconciles an unknown one with `{no_usage: true}`. `still_unknown` or an explicit `unknown` outcome retains the reservation and moves a stale `held` hold to `unknown`. Exceptions are audited and leave the hold blocking. Budget, outcome-record and audit updates are idempotent transactions; one application process is assumed.

An absent executor journal entry is not by itself permission to release a reservation. `lookup(hold_id)` atomically inserts a terminal `not_started` entry for an existing hold before returning that result. Its `BEGIN IMMEDIATE` transaction serializes with the executor's start claim, so a delayed `execute` observes the tombstone and cannot begin after reconciliation releases the hold. If execution won that race, the persisted `started` entry returns `still_unknown` until an outcome exists. Only `unknown` and stale `held` holds block new work; a young held reservation remains in flight and still counts against limits.

Routes (owned by E11-2, rendered by E11-5): `POST /instances/{id}/work-requests` (owner session and CSRF; the page is labelled simulated work) and `POST /pending-actions/{id}/confirm` (owner session and CSRF; calls `create_confirmation`). Chat and `/app-tools/*` have no route to either.

### WorkExecutorPort and the deterministic simulator (owner E11-2)

`WorkExecutorPort` provides:

- `execute(AuthorizedWork {work_id, instance_id, capability, payload, hold_id, connection_handle, destination}) -> ExecutorOutcome {status: succeeded | failed | not_started | unknown, measured_usage}`.
- `lookup(hold_id) -> ExecutorOutcome | still_unknown`. The argument is the globally unique authorized budget hold ID, not the tenant-scoped work ID.

The executor validates that the hold matches `instance_id` and `work_id`. It commits an `executor_journal` row with status `started` before any simulated provider effect or result production. It persists the resulting outcome and measured usage in a later transaction. A repeated execute returns the stored result without dispatching again; a started row with no result returns unknown. A hold already released or settled cannot acquire a new start claim. A missing journal entry on lookup becomes a committed `not_started` tombstone when the hold exists, preventing later execution of that hold. A nonexistent hold also returns `not_started`, and execute rejects it because no authorization exists.

`executor_journal` is owned by E11-2 and keyed by `hold_id` with a foreign key to `budget_hold`. It stores `started | succeeded | failed | not_started | unknown`, plus measured input/output tokens and compute minutes for definite outcomes. Journal state survives process restart. Migration `0008_executor_journal.sql` conservatively seeds `unknown` for pre-existing held/unknown operations with a `WorkRequestRecord`; previous process-memory absence cannot prove those operations never started. Such reservations stay blocked until a definite outcome can be established.

`FakeWorkExecutor` remains the only enabled implementation (`AICL_EXECUTOR_MODE=fake`). It makes no network or model call and derives its result from `payload.sim = {input_tokens, output_tokens, compute_minutes, outcome}` (defaults 0, 0, 0 and `succeeded`; usage may exceed the estimate to exercise over-measured settlement). Provider capabilities exercise the fake provider through `CredentialBroker.call`; no credential crosses the executor interface. The application composition passes its database explicitly. The no-argument test seam binds the process-default database on first use and retains it. Real provider idempotency, transport enforcement and authoritative outcome lookup remain future adapter work; this durable simulator does not enable real inference or compute.

### Safe disabled mode and startup rejection (enablement safeguard)

The only composition that starts is fake: `AICL_PROVIDER_MODE=fake`, `AICL_EXECUTOR_MODE=fake`, `AICL_CHAT_MODEL_MODE=fake`. Any other value (including `real`) fails startup with the message `provider enablement is not recorded`, because no real adapter exists in the code base and a separate human-approved enablement change must add one together with the recorded approval. No provider credential, client id or secret appears in the repository, CI, fixtures or `.env.example`; tests make no live calls. These modes cover provider, executor and chat-model adapters only. Magic-link email through the operator-configured SMTP server (E11-3) is the one real outbound edge of the application; it is distinct from Gmail, uses no provider credential of this design and is outside the rejected-adapter list.

## Process topology

One in-process service layer behind the single FastAPI application described in the control-plane document. Calls: connection pages and OAuth callback (E11-5 pages, E11-2 routes) → connection service → `SecretStore`, `ProviderOAuthPort`; work requests → `WorkAuthorization` → `authorize_destination`, `BudgetPort`, confirmation store → `WorkExecutorPort` → `CredentialBroker` → `ProviderOAuthPort`. The secret store, broker and revocation path are the only holders of credentials; the web layer, chat and the executor interface never import them. The OAuth callback is a browser redirect into the same process; there is no other channel. Transactions: state changes and their audit event commit together; the provider revoke call and the executor call are made outside a database transaction and their results recorded in a following transaction.

Authoritative table: [architecture.md](../architecture.md#consolidated-configuration). Rows owned here: `AICL_SECRET_ENCRYPTION_KEY` (required, startup fails when absent or not 32 base64 bytes), `AICL_PUBLIC_BASE_URL` (required, `https` outside test and development localhost; validation implemented in E11-1 `settings.py`), `AICL_PROVIDER_MODE`, `AICL_EXECUTOR_MODE`, `AICL_EXECUTOR_TIMEOUT_SECONDS`, `AICL_RECONCILE_INTERVAL_SECONDS` (`AICL_HOLD_STALE_SECONDS` is owned by E11-1, which cross-validates it against the other two). A missing secret key fails startup; an unavailable or corrupt secret at use denies and never falls back to a plaintext or default value.

## Verification pointers

E11-2 proves F2-S1 to F2-S11 with unit tests (host normalization and SSRF rules, scope table, digest binding, state/PKCE, redaction), integration tests with real SQLite and the fake provider and executor (attach rules, revoke including provider failure and crash sweep, gate order, confirmation single use and mismatch, over-measured settlement, unknown outcome, no credential in any result), and HTTP tests through the real application for the callback, work request and confirm routes. E11-5 reuses the gate through the production-wired browser journeys rather than re-testing its rules.
