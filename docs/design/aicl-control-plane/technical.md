# AICL control plane technical design

Scope: E11-1 (domain and control foundation) and the canonical creation service and first-party web-app tools owned by E11-2. Connection, network and dispatch contracts are in [connection-network-policy/technical.md](../connection-network-policy/technical.md); UI, sign-in and chat contracts are in [aicl-experience/technical.md](../aicl-experience/technical.md). Stack, layout, the consolidated configuration table and test layers are in [architecture.md](../architecture.md). Proposed source locations are under `backend/aicl/` and are labeled proposed until the code exists.

## Contracts

### Conventions

- Language Python 3.12; contracts are frozen dataclasses or pydantic v2 models with `extra="forbid"`; ports are `typing.Protocol` classes with a minimal fake each (stubs are prepared by the Development design worker, not by Design).
- Identifiers are lowercase UUID4 strings. Timestamps are timezone-aware UTC, serialized as ISO 8601 with `Z`. Time comes from a `Clock` port (`now() -> datetime`) so tests can control it.
- Money is an integer count of micro-USD (1 USD = 1,000,000). Floats and decimals never cross a contract boundary. Rounding of a computed cost is always up (ceiling).
- Every mutation takes the authenticated `AuthContext` as its first argument. No contract accepts a tenant or owner identifier from a client payload.
- Unit of work (owner E11-1): `db.transaction()` opens one `BEGIN IMMEDIATE` SQLite transaction and yields `conn`. Every mutating repository, `BudgetPort`, `ActionConfirmation` and `AuditLog` operation has a connection-scoped form `op(conn, ...)` that runs inside the caller's open transaction and never commits or rolls back by itself. The convenience form without `conn` opens its own transaction and calls the connection-scoped form. A composed operation (creation, an instance operation, the gate's step 9) calls the connection-scoped forms inside one `db.transaction()`, so all effects and the audit event commit or roll back together.
- Key pattern: every client idempotency key (`CreateInstanceRequest.idempotency_key`) and `work_id` matches `^[A-Za-z0-9_-]{16,64}$`; any other character, including `:`, is `validation_failed`. Derivations used by first-party surfaces (all conform): wizard `wiz_<32 lowercase hex>` (36 characters, from a per-form UUID4), simulated-work form `work_<32 lowercase hex>` (37), chat `chat_<32 lowercase hex of chat_session_id>_<turn>` with `turn` a decimal integer from 1 to 999999 (39 to 44 characters).

### Error taxonomy (shared by every operation and HTTP route)

Errors are a structured object `{error, message, ...}`; `message` is safe to show and never contains secrets, tokens or another tenant's data.

| error | HTTP | Extra fields | Meaning |
|---|---|---|---|
| `unauthenticated` | 401 | none | No valid session or `AuthContext` expired |
| `not_found` | 404 | none | The object does not exist OR belongs to another tenant (indistinguishable) |
| `validation_failed` | 422 | `field_errors: [{field, code}]` | Malformed or out-of-bounds input, unknown template, capability or argument |
| `conflict` | 409 | `current_version` or `existing_result_id` | Stale `expected_version`, or the same idempotency key with a different payload |
| `invalid_transition` | 409 | `from`, `action` | Lifecycle action not in the transition table |
| `invalid_state` | 409 | `lifecycle` | Mutation not allowed in the current state (for example any mutation of an `archived` instance) |
| `denied` | 403 | `reason` | Dispatch gate or confirmation denial; `reason` is one of the gate reasons below |
| `unavailable` | 503 | none | A required dependency (database, lock, price table, secret store) could not be used; the request fails closed |

### AuthContext (owner E11-1)

`AuthContext {owner_id, tenant_id, session_id, expires_at}` is a frozen dataclass created only by an `AuthProvider` (Protocol: `resolve(request_headers_and_cookies) -> AuthContext | None`). E11-1 owns the dataclass, the Protocol and a `FixedAuthProvider` test double (returns configured contexts for fixture cookies); E11-3 owns the real `SessionAuthProvider` (see the experience document). Rules:

- MVP tenant rule: one tenant per owner and `tenant_id == owner_id` (both are the owner's UUID). The two fields stay separate in every model so teams can be added later without changing contracts. "Same owner" (connection sharing) means equal `owner_id`.
- An expired or missing context is `unauthenticated`. Services never read `tenant_id`, `owner_id` or `session_id` from request bodies, query strings, headers other than the session cookie, or tool arguments; such fields are rejected as `validation_failed` (`unknown_argument`) by schemas with `extra="forbid"`, and ignored on form posts.
- Every repository query is filtered by `auth.tenant_id`. A row of another tenant yields `not_found`, never `denied` or `forbidden`, and the audit log records an `access.denied` event with only the object kind.
- Browser-originated mutations additionally require a CSRF token bound to the session, verified through the `CsrfVerifier` below.

### CsrfVerifier (owner E11-1)

`CsrfVerifier` (Protocol): `token_for(session_id) -> str` and `verify(auth, submitted_token, origin | None) -> bool` (constant-time comparison; when `origin` is present it must equal `AICL_PUBLIC_BASE_URL`). E11-1 owns the Protocol, the shared request dependency `require_csrf` that every non-GET route uses (E11-2 `/app-tools/*`, work-request, confirm and OAuth begin routes; E11-3 forms and logout; E11-4 chat; E11-5 forms), and `FixedCsrfVerifier`, a fixed fake that accepts one configured token only for the seeded fixture sessions of the test server and returns false for any other session. E11-3 owns `HmacCsrfVerifier` (token `HMAC-SHA256(AICL_SESSION_SECRET, session_id)`), the only production implementation; once it is registered the test composition routes real `aicl_session` sessions to it and only seeded fixture sessions to the fixed fake.

### AppComposition (owner E11-1)

`backend/aicl/app.py::create_app(settings, ports=None) -> FastAPI` is the only composition root. E11-1 owns the skeleton: it loads and validates `Settings` (the whole configuration table), runs migrations, imports the price table, builds `AppContext {settings, db, clock, auth_provider, csrf_verifier, ports}` and registers the routers returned by `backend/aicl/routes.py::ROUTE_FACTORIES`, an ordered tuple of `(AppContext) -> APIRouter` callables that is empty in E11-1 and extended by one line from each ticket that adds routes (E11-2, E11-3, E11-4, E11-5). `backend/aicl/ports.py` is the registry in which each ticket registers its real implementations by port name. `Ports` is a frozen typed model with one field per port name. Required in every composition: `auth_provider`, `csrf_verifier`, `clock`, `secret_store`, `credential_broker`, `provider_oauth`, `work_executor`, `resolver`, `magic_link_sender`, `chat_model`. Test-only (present only when both `AICL_TEST_MODE=1` and `AICL_ENVIRONMENT=test`): `mail_capture` and `clock_control`. The database-backed services (repositories, `BudgetPort`, `AuditLog`, confirmations, `WorkAuthorization`, `NetworkPolicy`) are built from `AppContext.db`, not injected.

`build_ports(settings) -> Ports` is the default used when `ports=None`: leaf ports resolve from the registry in `ports.py` by mode (`fake` registers `FakeProviderOAuth`, `FakeWorkExecutor`, `ScriptedChatModel` and the fake `Resolver`); `magic_link_sender` is `CaptureMagicLinkSender` when both test flags are set and `SmtpMagicLinkSender` otherwise (which needs `AICL_SMTP_HOST`, else startup fails); `auth_provider` and `csrf_verifier` resolve to the E11-3 `SessionAuthProvider` and `HmacCsrfVerifier` once registered (before that, the `Fixed*` doubles are used only when both test flags are set). A required port with no registered implementation fails startup (`composition incomplete: <port>`). The `ports` argument exists only for test overrides (the `Fixed*` doubles in the E11-1 to E11-4 tests); no production entry point passes it.

`python -m aicl.test_server` (E11-1, architecture document) is `create_app(test settings)` with the default `build_ports` plus the test-only `/__test__/*` routes, so the E11-5 journeys use the registry-built real services with no in-test replacement. E11-2 to E11-4 test their routes through this app.

The third extension point is `backend/aicl/hooks.py::STARTUP_HOOKS`, an ordered tuple of `(AppContext) -> Hook` factories, empty in E11-1. A `Hook` has `start()`, `stop()` and `run_once()` (tests drive `run_once()` with `FakeClock`). Startup order: migrations, price import, port build, hooks in tuple order (E11-2 registers `RevocationSweeper` first and `HoldReconciler` second; E11-3 registers `MagicLinkPurge`), then the routers. Failure rule, fail closed: an exception in the startup sweep of secrets of revoked connections fails startup; a reconciler exception is audited and leaves its holds blocking. The MVP assumes one uvicorn worker, and the sweep and reconcile steps stay idempotent under `BEGIN IMMEDIATE`.

E11-5 proves the composition with the test flags on (the settings `aicl.test_server` uses): `create_app(settings)` with `ports=None` resolves every required port, registers every `ROUTE_FACTORIES` entry and every `STARTUP_HOOKS` hook, and fails startup when a required port is missing. This is test-composition evidence: production differs only by the absent `/__test__/*` routes, the SMTP sender instead of the capture sender, the absent seeded session and the absent fake OAuth page.

### Instance model (owner E11-1)

`AgentInstance {id, tenant_id, owner_id, template_id, name, instructions, lifecycle, gated_reason, gate_context, version, limits, network_domains, created_at, updated_at}`:

- `lifecycle`: `draft | active | paused | archived`. `gated_reason`: `null` or one of `budget_exhausted`, `budget_unavailable`, `capability_disabled`, `connection_revoked`, `connection_reauthorization_required`, `network_denied`. `version` starts at 1 and increments by one on every committed change of the instance, its grants, limits, domains or attachments.
- `gate_context`: `null` or `{capabilities: [capability], host_hash12 | null}`, stored with a persisted `gated_reason` so the control can be re-evaluated later: `capabilities` for `capability_disabled`, `connection_*` and `network_denied` (a revoked connection can have served several capabilities of the instance); `host_hash12` (first 12 hex characters of the sha256 of the denied host) for `network_denied`. It never holds a URL, path, query, payload or credential. E11-1 owns the set and clear primitives (`set_gated(conn, ...)`, `clear_gated(conn, ...)`); E11-2 decides when to call them.
- `limits`: `{inference_daily_micro_usd, inference_monthly_micro_usd, compute_daily_micro_usd, compute_monthly_micro_usd}`, all integers in `[0, 1_000_000_000_000]`, default 0 (D11-5). Within a category monthly must be greater than or equal to daily.
- `network_domains`: tuple of owner-added exact hosts (sorted, at most 20), read through `NetworkPolicy` (E11-2).
- `CapabilityGrant {instance_id, capability, enabled}` for the catalog capabilities `inference`, `gmail.read`, `gmail.send`, `reddit.read`, `reddit.post`, `network.fetch`; all rows exist and default to `enabled=false`.
- Derived `status` for display and read models: the lifecycle when it is not `active`; `gated` when active and (`gated_reason` is set or a blocking hold exists, shown as `reconciliation_pending`; a blocking hold is an `unknown` hold or a `held` hold older than `AICL_HOLD_STALE_SECONDS`); otherwise `active`. `gated_reason` is never set on a draft, paused or archived instance by a denial (the denial is `instance_not_active`); an existing reason is retained across pause and resume and shown only while `lifecycle=active`.

### Template catalog (owner E11-2, data in E11-1 constants)

The MVP catalog has one template: `default` (version 1), capabilities as above. Configuration constraints enforced by the canonical creation service: `name` is 1 to 80 characters after trimming and NFC normalization; `instructions` is 0 to 4,000 characters; control characters other than newline and tab are rejected; `enabled_capabilities` is a set of catalog capability ids (unknown id is `validation_failed`). Unknown `template_id` is `validation_failed`.

### CreateInstanceRequest and CreateInstanceResult (owner E11-2)

`CreateInstanceRequest {idempotency_key, template_id, name, instructions, enabled_capabilities}` with `idempotency_key` 16 to 64 characters of `[A-Za-z0-9_-]` (key pattern in Conventions; the length bound is enforced, so a shorter or longer key is `validation_failed`). There is no tenant, owner, credential or confirmation field. `CreateInstanceResult {instance: InstanceSnapshot, created: bool, audit_event_id: int}` where `created=false` on an idempotent replay.

`create_instance(auth, request, *, actor_kind="owner", surface="ui") -> CreateInstanceResult` is the one canonical creation function (`actor_kind` and `surface` are set by the server-side caller, `wizard` by the wizard route and `chat` by the chat orchestrator, never by a client payload or tool argument, and are recorded in the `instance.created` event) used by the wizard (E11-3), the web-app tool `create_instance` (E11-2, used by chat in E11-4) and any other first-party surface. In one database transaction it validates, then inserts the draft instance (version 1, all limits 0), one grant row per catalog capability (enabled per the request), and the `instance.created` audit event. Idempotency is scoped to `(tenant_id, idempotency_key)`: a replay with an identical request digest returns the stored result with `created=false`; a different digest is `conflict` with `existing_result_id`. Chat derives its key as `chat_<32 hex of chat_session_id>_<turn>` and the wizard as `wiz_<32 hex>` from a per-form hidden value (both conform to the key pattern), so a retried turn or double submit creates one instance. Creation never activates, never attaches connections and never grants authority beyond the explicit capability flags.

### InstanceSnapshot (owner E11-2)

`InstanceSnapshot {id, template_id, name, instructions, lifecycle, status, gated_reason, version, limits, capabilities: {capability: bool}, network_domains, attachments: [{capability, connection_id, connection_display_name, connection_status}], created_at, updated_at}` is the lean, tenant-filtered view of one instance. It contains no `tenant_id`, `owner_id`, budget, usage, audit entries, pending actions, `secret_ref` or credential. E11-2 builds it with `read_instance_snapshot(auth, instance_id)` (and a `conn` form) from the E11-1 repositories and the E11-2 attachment repository; `status` is the derived status above. It is the only instance shape returned by `create_instance`, by every `MutationResult` and by the `read_instance` tool (so chat sees only this snapshot). E11-5 `InstanceDetailView` composes it with budget, usage history, audit and pending actions (experience document) and does not redefine it.

### Instance mutation operations (owner E11-2, `InstanceOperations`)

All operations: `(auth, instance_id, expected_version, ...) -> MutationResult {instance: InstanceSnapshot, changed: bool, audit_event_id: int | null}`; owned by the creation/operations service in E11-2 and invoked by UI form handlers (E11-3 for the wizard follow-up, E11-5 for management pages). A stale `expected_version` is `conflict` with `current_version` and no effect. A request that would not change state (same capability value, domain already present or absent) and carries the current version returns `changed=false`, no version bump and no audit event. Each committed change bumps `version` and appends one audit event in the same transaction. Mutating an `archived` instance is `invalid_state`.

| Operation | Extra request fields | Effect and rules |
|---|---|---|
| `set_lifecycle` | `action: activate \| pause \| resume \| archive` | Applies the transition table below; anything else is `invalid_transition` |
| `set_capability` | `capability`, `enabled` | Updates the grant. Calls `evaluate_gate_control` and clears a persisted gate when the control now permits work |
| `set_limits` | `limits` (the four fields) | Replaces the limits after validation. Lowering below current spend is allowed and takes effect at the next dispatch. Calls `evaluate_gate_control` per the gating rule |
| `add_network_domain` / `remove_network_domain` | `host` | Owner `network.fetch` domain edit; add validates with `normalize_owner_domain` (connection document). Calls `evaluate_gate_control` |
| `resolve_gate` | none | Re-evaluates the persisted gate for every reason and clears it only if the control now permits work, otherwise `denied` with `gate_unresolved` (gating rule). Without a persisted gate it returns `changed=false` |
| `attach_connection` / `detach_connection` | `capability`, `connection_id` | Defined in the connection document; same version and audit rules |

Lifecycle transition table (an unlisted pair is `invalid_transition`; `archived` is terminal):

| From | `activate` | `pause` | `resume` | `archive` |
|---|---|---|---|---|
| `draft` | `active` | no | no | `archived` |
| `active` | no | `paused` | no | `archived` |
| `paused` | no | no | `active` | `archived` |
| `archived` | no | no | no | no |

Activation has no preconditions other than ownership and `draft` state: a zero-budget active instance is valid and is gated at its first work request. `paused` is only ever set by the owner; the gate never pauses an instance.

Gating rule, following D11-8 literally: only the owner clears a gate, and only when the control now permits work. A daily or monthly window rollover never clears `gated_reason`. One function, `evaluate_gate_control(conn, instance) -> permits | still_denied` (owner E11-2), re-evaluates the persisted reason with its `gate_context`: `budget_exhausted` and `budget_unavailable` permit when `read_budget` is readable, a price-table version is effective and all four windows have `available > 0` (a zero limit is exhausted, D11-5); `capability_disabled` permits when every grant in `gate_context.capabilities` is enabled; `connection_revoked` and `connection_reauthorization_required` permit when every capability in `gate_context.capabilities` has an active attachment on an `active` connection; `network_denied` permits when `network.fetch` is enabled and `network_domains` contains a host whose sha256 prefix equals `gate_context.host_hash12`. The owner clears a gate by (a) a committed mutation that fixes the control (`set_limits`, `set_capability`, `attach_connection`, `add_network_domain`), which calls `evaluate_gate_control` in the same transaction and clears the reason only when it permits work, or (b) `resolve_gate`, which calls the same function for every reason: when it permits, the reason and context are cleared (version bump, `instance.gate_resolved` committed); otherwise nothing changes and the result is `denied` with reason `gate_unresolved` (audited as `instance.gate_resolved` with outcome `denied`). There is no acknowledgement path that clears a gate while its control still denies, so an instance shown as `active` can do work. Only an owner-resolvable network denial (`host_not_allowed` for `network.fetch`) persists `network_denied`; other network denials (scheme, port, userinfo, address, redirect, method, path, policy) deny that request with the rule in the audit event and persist nothing, because the destination, not the owner's control, failed. `reconciliation_pending` is derived, not persisted, and disappears when no blocking hold remains. Persisted `gated_reason` and `gate_context` store only machine values, never a destination, payload or credential.

### Gate reasons (denial vocabulary, owner E11-2 for the gate; E11-1 for budget reasons)

`instance_not_active`, `capability_disabled`, `confirmation_required`, `confirmation_expired`, `confirmation_used`, `confirmation_mismatch`, `connection_unavailable`, `network_denied`, `budget_exhausted`, `budget_unavailable`, `price_unavailable`, `estimate_missing`, `reconciliation_pending`, `gate_unresolved`, `check_unavailable`. Those that set `gated_reason` (with `gate_context`): `capability_disabled`, `connection_unavailable` (as `connection_revoked` or `connection_reauthorization_required`), `network_denied` (only `host_not_allowed` for `network.fetch`), `budget_exhausted`, `budget_unavailable` (also used for `price_unavailable`). Confirmation, estimate, not-active and reconciliation denials do not persist a reason.

### BudgetPort (owner E11-1)

Estimate source: the caller (the dispatch gate) supplies a bounded `Estimate {inference_input_tokens, inference_output_tokens, compute_minutes}` (nonnegative integers, the maximum the work may use). The work request declares it; a missing or unbounded estimate is `estimate_missing`. Cost of an estimate or of measured usage is computed by the `PriceTable` with integer ceiling arithmetic. Inference cost counts against the inference limits and compute cost against the compute limits; a capability does not gate compute separately (compute is a metered resource of any dispatched work).

Shapes:

- `Hold {id, instance_id, work_id, price_table_version, inference_micro_usd, compute_micro_usd, window_day, window_month, state, created_at, state_changed_at}` with `state` of `held | settled | released | unknown` (transitions: `held`→`settled`, `released` or `unknown`; `unknown`→`settled` or `released`; `settled` and `released` are terminal); `window_day` is the UTC date and `window_month` the UTC `YYYY-MM` of `created_at`.
- `Usage {hold_id, instance_id, inference_input_tokens, inference_output_tokens, compute_minutes, inference_micro_usd, compute_micro_usd, price_table_version, window_day, window_month, recorded_at}`; usage is never rewritten.
- `BudgetView {instance_id, limits, windows: {day, month}, per category and window: {limit, settled, held, available}, blocking_hold_count, price_table_version}` where `held` sums every outstanding `held` and `unknown` hold and `available = max(0, limit - settled - held)`.

Operations (every mutation has a connection-scoped form `op(conn, ...)` for the caller's unit of work, see Conventions, and a convenience form that opens its own `BEGIN IMMEDIATE` transaction; a lock timeout or any storage error is `unavailable` and denies):

- `reserve(conn, instance_id, work_id, estimate) -> Hold`: runs in the caller's transaction (the gate's step 9 shares it with the confirmation consumption); idempotent on `(instance_id, work_id)`; a repeat returns the original hold even if terminal, a repeat with a different estimate is `conflict`. In the same transaction it selects the effective price-table version, prices the estimate, sums settled usage plus outstanding `held` and `unknown` holds for the inference-day, inference-month, compute-day and compute-month windows, and creates the hold only if every one of the four checks passes. Concurrent reservations that jointly exceed any limit cannot both succeed because the writer lock serializes them. Denials: `budget_exhausted` (limit would be exceeded or is 0), `budget_unavailable` (limits missing or invalid, unreadable state), `price_unavailable`, `reconciliation_pending` (the instance has a blocking hold: an `unknown` hold or a `held` hold older than `AICL_HOLD_STALE_SECONDS`). A `held` hold younger than that is in-flight work and counts against the limits but does not block.
- `settle(conn, hold_id, measured_usage) -> Usage` (the convenience form omits `conn`): idempotent per hold; same measured usage returns the stored `Usage`, different measured usage on a settled hold is `conflict`. Settling a `released` hold (terminal) is `conflict`, and a `budget.late_settlement` audit event records the late usage so it is never silently dropped. Cost uses the price-table version stored on the hold, not the current one. The hold becomes `settled` and its reservation is released; attribution stays in the hold's original windows even if settlement happens after midnight. If measured cost exceeds the hold, the full measured cost is recorded (never truncated), the window may exceed its limit, a `budget.overrun` audit event is appended, and the instance is gated `budget_exhausted` at the next dispatch.
- `mark_unknown(conn, hold_id)`: valid from `held` (and a no-op on `unknown`); idempotent; the hold keeps its full reserved amount in all windows until reconciled and blocks new reservations for that instance.
- `reconcile(conn, hold_id, outcome)`: accepts a hold in `unknown` and `outcome` is `{measured_usage}` (then behaves like `settle`) or `{no_usage: true}` (releases the hold with zero usage). Only the internal reconciler (E11-2) calls it, using the executor's `lookup(work_id)`; it is idempotent. Failure to reconcile leaves the hold in place and the instance denied while the hold is blocking.
- `release(conn, hold_id)`: valid from `held` or `unknown`, for work that the executor reports as definitely not started (including a `work_id` the executor never saw); idempotent.
- `settle` is valid from `held` or `unknown` only (a `released` hold gives `conflict` as above).
- `read_budget(instance_id) -> BudgetView`: read-only; used by E11-5 projections.

Only `unknown` holds and stale `held` holds (older than `AICL_HOLD_STALE_SECONDS`, measured from `created_at` with the `Clock`) block new work for the instance; every outstanding `held` or `unknown` hold also keeps its reserved amount in every applicable window. A new owner mutation or window rollover does not release a hold. Stale `held` handling belongs to the E11-2 reconciler (connection document): it calls `mark_unknown` and then `reconcile`, or `release` directly when `lookup` reports `not_started`. `AICL_HOLD_STALE_SECONDS` is owned by E11-1 and passed to `BudgetPort` as a constructor argument; E11-1 `settings.py` requires it to exceed `AICL_EXECUTOR_TIMEOUT_SECONDS + AICL_RECONCILE_INTERVAL_SECONDS`, so the reconciler never looks up work that may still be running.

### PriceTable (owner E11-1)

Source: an operator-managed JSON file named by `AICL_PRICE_TABLE_PATH`, imported at startup into insert-only tables (`price_table_version`, `price_rate`). There is no environment variable that selects a version; selection is by effective date.

```json
{"version": "2026-10-01", "effective_from": "2026-10-01T00:00:00Z",
 "rates": [{"meter": "inference.input_tokens", "unit_size": 1000, "micro_usd": 1000},
           {"meter": "inference.output_tokens", "unit_size": 1000, "micro_usd": 3000},
           {"meter": "compute.minutes", "unit_size": 1, "micro_usd": 5000}]}
```

Validation: `version` unique non-empty string `[A-Za-z0-9._-]{1,32}`; `effective_from` UTC timestamp; all three meters present exactly once; `unit_size` positive integer; `micro_usd` nonnegative integer; no floats. Cost for a meter is `ceil(units * micro_usd / unit_size)`.

Immutability: the import stores the SHA-256 of the canonical JSON next to the version. Re-importing the same version with a different hash is a startup failure; database triggers reject `UPDATE` and `DELETE` on both tables. A price change is a new version with a later `effective_from`. The effective version for a request is the one with the greatest `effective_from` not later than `now`.

Failure behavior: at startup, a missing file, invalid schema, hash conflict, or no version effective at startup time fails startup. At use, no version effective at `now`, or a missing meter, denies the reservation as `price_unavailable` (never a default price). Each hold and usage row stores the applied version, so historical USD totals stay explainable.

### AuditEvent (owner E11-1)

`AuditEvent {seq, id, tenant_id | null, owner_id | null, instance_id | null, connection_id | null, event_type, actor_kind, outcome, reason | null, details, occurred_at}`. `seq` is a strictly increasing integer from the table's autoincrement key and is the ordering authority. `actor_kind` is `owner | chat | system | gate`; `outcome` is `committed | denied`. `tenant_id` and `owner_id` are null only for pre-authentication system events (`actor_kind=system`, event types `auth.link_rate_limited` and `auth.link_rejected`, raised before any owner exists; `access.denied` is reserved for authorization denials of an authenticated owner); every other event requires both. Events with a null tenant are never returned by `list_for_instance` or `list_for_owner` (the readers filter `tenant_id = auth.tenant_id`, which a null never equals), so only an operator reading the database sees them.

Event types: `instance.created`, `instance.lifecycle_changed`, `instance.capability_changed`, `instance.limits_changed`, `instance.domain_added`, `instance.domain_removed`, `instance.gated`, `instance.gate_resolved`, `connection.created`, `connection.attached`, `connection.detached`, `connection.revoked`, `connection.provider_revoke_succeeded`, `connection.provider_revoke_failed`, `confirmation.requested`, `confirmation.created`, `confirmation.used`, `work.denied`, `work.dispatched`, `budget.reserved`, `budget.settled`, `budget.unknown`, `budget.reconciled`, `budget.overrun`, `budget.late_settlement`, `auth.signed_in`, `auth.signed_out`, `auth.link_rate_limited`, `auth.link_rejected`, `access.denied`.

Redaction allow-list: `details` may contain only these keys (any other key is dropped by the writer, and a test asserts it): `from`, `to`, `action`, `capability`, `enabled`, `version`, `limit_field`, `old_micro_usd`, `new_micro_usd`, `host` (owner-added domain), `provider`, `connection_id`, `hold_id`, `micro_usd`, `price_table_version`, `denial_reason`, `confirmation_id`, `payload_digest_prefix` (first 12 hex characters), `template_id`, `surface` (`wizard | chat | ui`), `target_kind`, `count` (an integer counter), `reason_code` (a fixed machine value such as `unknown`, `expired`, `used`, `rate_limit`), `token_hash_prefix` or `email_hash_prefix` (first 8 hex characters of the hash, pre-authentication events only). Never recorded: instructions, instance names, email addresses, tokens, authorization codes, secrets, message or post bodies, full payloads, full digests, destination URLs with paths or queries.

Append-only: the only writer is `AuditLog.append(conn, event)`, called inside the same transaction as the change it records (so a rolled-back change leaves no event). Denial events append in their own transaction because no state changes. Database triggers abort `UPDATE` and `DELETE`. Readers are `list_for_instance(auth, instance_id, after_seq, limit<=100)` and `list_for_owner(auth, after_seq, limit<=100)`, newest first, always filtered by `auth.tenant_id`; E11-5 uses them for the audit history views. Pre-authentication events record only `reason_code`, `count` and a hash prefix, never an email address, token, client IP or IP hash. The rate-limit denial appends at most one `auth.link_rate_limited` event per email-hash or IP-hash window (`count` is set at append, because the log is append-only); later over-limit requests in the window append nothing, so a flood cannot grow the log. Appenders by ticket: E11-1 (budget, instance primitives, gate-state events), E11-2 (creation, operations, connection, confirmation, gate events), E11-3 (`auth.*`, including `auth.link_rate_limited`). Consumers of the `AuditEvent` contract: E11-2, E11-3 (appends `auth.*`), E11-5 (readers).

### ActionConfirmation and PendingAction (owner E11-1)

Per D11-1, `gmail.send` and `reddit.post` need a per-action owner confirmation in addition to an enabled capability and available limits.

- `payload_digest = sha256(canonical_json({instance_id, capability, payload}))` where canonical JSON uses sorted keys, no whitespace, UTF-8. The dispatch gate computes the digest itself from the request; callers never supply it.
- `PendingAction {id, instance_id, tenant_id, capability, payload_digest, preview, created_at}`: created by the gate when it denies `confirmation_required`. `preview` is a bounded allow-listed summary (for example recipient domain, subreddit, body length), never the body.
- `ActionConfirmation {id, pending_action_id, instance_id, capability, payload_digest, owner_id, tenant_id, created_at, expires_at, used_at | null}`: single use, bound to exactly one digest, expires after `AICL_CONFIRMATION_TTL_SECONDS` (default 300).
- Creation: `create_confirmation(auth, pending_action_id)` (with a `conn` form) creates it only from an owner-authenticated, CSRF-protected UI form request. It is not in the web-app tool registry, is not reachable through `/app-tools/*`, and the chat orchestrator holds no reference to it, so chat text or a tool call cannot create or approve one. It is idempotent per pending action (a second call returns the existing unused unexpired confirmation).
- Consumption: `consume_confirmation(conn, confirmation_id, computed_digest, now) -> bool` is the connection-scoped single conditional update (`used_at IS NULL AND expires_at > now AND payload_digest = computed`; it returns false when no row changed). The gate calls it with the same `conn` as `BudgetPort.reserve(conn, ...)` inside one `db.transaction()` (WorkAuthorization step 9), so a failed reservation rolls back the consumption and a failed consumption rolls back the reservation, so a denial earlier or later in the check order never burns a confirmation wrongly and two concurrent dispatches cannot both use it. The gate's earlier existence check (step 6) is read-only; the update here is the authority. A missing confirmation is `confirmation_required` (and a `PendingAction` is created or reused); an expired one is `confirmation_expired`; a used one is `confirmation_used`; one for a different digest (changed payload) is `confirmation_mismatch`. Each is audited (`confirmation.requested`, `confirmation.created`, `confirmation.used`, `work.denied`); a denial audit and any `gated_reason` write (`set_gated`) use their own transaction after the step-9 transaction has rolled back, because no other state changed.
- If the executor reports the work definitely did not send, the hold is released but the confirmation stays consumed; the owner must confirm again.

### WebAppToolSchemas (owner E11-2)

First-party web-app tools (not a public or external MCP API) are served at `POST /app-tools/{name}` for same-origin authenticated callers (session cookie plus `X-CSRF-Token`). The registry is a static dict of name to pydantic input model and handler; the same handlers back the wizard where applicable. Every input model forbids extra fields, so `tenant_id`, `owner_id`, `session_id`, credential fields and confirmation fields are rejected as `validation_failed`/`unknown_argument`. Tool list and schemas:

| Tool | Input | Result |
|---|---|---|
| `list_templates` | `{}` | the catalog (`template_id`, `name`, `capabilities`, constraints) |
| `create_instance` | `CreateInstanceRequest` fields | `CreateInstanceResult` |
| `read_instance` | `{instance_id}` | `InstanceSnapshot` only (the caller's tenant only; no budget, usage, audit or pending actions) |

No other operation is a tool. Lifecycle, capability, limit, domain, connection, confirmation and gate operations are owner-UI form operations only, so chat cannot reach them. Tools return the error taxonomy above. The registry exposes no connection, secret, budget-writing or confirmation operation.

## Incremental composition port delivery (DR-30)

`Ports` is an incremental registry, not a promise that every future-ticket port exists in E11-1. `REQUIRED_PORTS` begins as `(clock,)` in E11-1 and is extended only by the ticket that introduces and registers a port. `build_ports(settings)` validates exactly the currently registered tuple; an unregistered future port never blocks an earlier ticket's `create_app` startup. E11-5 asserts the final required tuple: `clock`, `secret_store`, `credential_broker`, `provider_oauth`, `work_executor`, `resolver`, `magic_link_sender`, and `chat_model`.

Ownership is: E11-1 owns `Clock` and the base registry; E11-2 owns `SecretStore`, `CredentialBroker`, `ProviderOAuthPort`, `WorkExecutorPort`, and `Resolver` with their fakes; E11-3 owns `MagicLinkSender`, `CaptureMagicLinkSender`, and the capture route; E11-4 owns `ChatModelPort`. E11-1's test routes are limited to seeded-session and clock facilities. The test server gains capture routes only when E11-3 registers its sender. This preserves the existing dependencies and waves.

## Process topology

One FastAPI process (plus Uvicorn) serves HTML pages, form posts, `/app-tools/*` and the chat API. All services run in-process and share one SQLite database file (WAL mode, `busy_timeout` 5000 ms, foreign keys on). The call direction is: routes (E11-3/E11-4/E11-5) → `InstanceOperations` and `create_instance` (E11-2) → control-plane repositories, `BudgetPort`, `AuditLog` (E11-1). The authenticated `AuthContext` is resolved once per request by the configured `AuthProvider` and passed down explicitly. The budget controller owns holds, usage and the price table; UI projections only call `read_budget` and the audit readers. Transactions: each operation is one SQLite transaction (`BEGIN IMMEDIATE` for anything that writes), with the audit append inside it. There is no cross-process channel in the MVP; the reconciler (owner E11-2, connection document) is a `STARTUP_HOOKS` hook that runs once at startup and then every `AICL_RECONCILE_INTERVAL_SECONDS` in-process. E11-1 supplies only the `BudgetPort` operations it calls.

## Configuration

The authoritative variable table is in [architecture.md](../architecture.md#consolidated-configuration). Rows owned here (E11-1 implements the whole `settings.py` validation, including rows whose behavior is delivered by later tickets): `AICL_ENVIRONMENT`, `AICL_TEST_MODE`, `AICL_DATABASE_URL`, `AICL_PRICE_TABLE_PATH`, `AICL_CONFIRMATION_TTL_SECONDS`, `AICL_HOLD_STALE_SECONDS` (used by `BudgetPort`). Startup fails on an invalid environment or test-mode combination, an `AICL_HOLD_STALE_SECONDS` not greater than `AICL_EXECUTOR_TIMEOUT_SECONDS + AICL_RECONCILE_INTERVAL_SECONDS`, a missing or unreadable database path, a missing or invalid price table, or a failed schema migration. The architecture table lists every other row with the ticket that owns its behavior; E11-1 validates all of them at startup. Per instance, default limits are 0 and enforcement is at use: unavailable budget state, unknown price or invalid limits deny the request. `PRICE_TABLE_VERSION` no longer exists. No real inference, compute, provider or chat-model adapter exists in this feature; the default and only composition uses the fake ports (safe disabled mode). The one real outbound edge of the application is magic-link email through the operator-configured SMTP server (experience document); it is not Gmail and not a provider adapter.
