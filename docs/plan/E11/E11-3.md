# E11-3: Authenticated workspace and agent-creation wizard

## Acceptance criteria
E11-3.AC1 maps F3-S1,F3-S2,F3-S3,F3-S5,F3-S8; test and browser.

## Dependencies
E11-1, E11-2.

## Design
Wizard, landing, sign-in and workspace shell. Implements the real `SessionAuthProvider` (magic link, session cookie, logout, `SmtpMagicLinkSender` as the one real outbound edge, with test capture) behind the E11-1 `AuthProvider` Protocol and `HmacCsrfVerifier` behind the E11-1 `CsrfVerifier` Protocol. Feature: aicl-experience (F3-S1, F3-S2, F3-S3 wizard half, F3-S5 wizard creation, F3-S8).

## Solution approach
Server-rendered landing, sign-in and verification pages, workspace empty state with **Create with wizard** and **Create with chat**, and the wizard form that posts to E11-2 `create_instance` with a per-form idempotency key. Implement the token, rate-limit, no-existence-leak, cookie and CSRF rules from the experience document, register the routers and real ports through the E11-1 extension point, and test them through the E11-1 `create_app` and test server. Email hashes use `AICL_IDENTITY_HMAC_KEY`; session and CSRF tokens use `AICL_SESSION_SECRET`. Pre-authentication denials append `auth.link_rejected` or `auth.link_rate_limited` (at most one rate-limit event per email-hash or IP-hash window, `count` set at append; `access.denied` is reserved for authorization denials) with null tenant and owner and only allow-listed `details`. `requested_ip_hash` is an HMAC under a subkey derived from `AICL_IDENTITY_HMAC_KEY`, and a `MagicLinkPurge` hook registered in `STARTUP_HOOKS` deletes `magic_link` rows expired for more than 24 hours at startup and hourly (`run_once()`). The wizard key is `wiz_<32 hex>` and the wizard has no budget, connection or credential field.

## Contracts
Own SessionAuthProvider (with `HmacCsrfVerifier` and `MagicLinkSender`) in `docs/design/aicl-experience/technical.md`. Consume CreateInstanceRequest, CreateInstanceResult, InstanceSnapshot, AuthContext, AgentInstance, AuditEvent, CsrfVerifier and AppComposition. Configuration rows owned for behavior: AICL_SESSION_SECRET, AICL_IDENTITY_HMAC_KEY, AICL_SESSION_TTL_SECONDS, AICL_MAGIC_LINK_TTL_SECONDS and AICL_SMTP_*; AICL_ENVIRONMENT and AICL_TEST_MODE belong to E11-1, which validates every row (table in `docs/design/architecture.md`).

## Verification
Integration tests: magic-link TTL, single use, hash-only storage under `AICL_IDENTITY_HMAC_KEY` (session secret rotation does not change the owner), identical responses for known and unknown emails and rate limits, a flood of over-limit requests appending exactly one `auth.link_rate_limited` event per window, a keyed `requested_ip_hash` (not an unkeyed SHA-256), the purge of expired `magic_link` rows, pre-authentication audit events with null identity that no owner reader returns, cookie flags, logout invalidation, `HmacCsrfVerifier` and ignored client tenant, cross-tenant `not_found`; startup rejection of test mode outside the test environment is the E11-1 check and is reused. One browser journey (real magic-link flow, not the seeded session): landing, sign-in with the captured link, wizard creation of a draft instance, field-error denial and, for a second user, the workspace empty state (the non-empty list and instance read page are E11-5's; cross-tenant `not_found` stays at integration level).
